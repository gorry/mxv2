# 更新チェック（アップデートの検知）

新しいバージョンが公開されたことを、アプリ自身が気付いて利用者に知らせる
仕組み。2026-09-24 に、調査 → 仕様決定（ユーザー） → 実装 → 検証まで行った。
ここではその経緯と、実装の構成・判断・検証方法をまとめる。

---

## 0. 要約

| 項目 | 内容 |
|---|---|
| 情報源 | GitHub Releases API `https://api.github.com/repos/gorry/mxv2/releases/latest` |
| 頻度 | 1 日 1 回（確かめ始めた時点で次を 24 時間後へ送る） |
| 実行 | 作業スレッドで通信・解析・比較 → メインスレッドが Poll で拾ってダイアログ |
| 更新の判定 | `Profile.ini` の `[Version] Text` と最新リリースのタグ名を数の並びとして比べ、タグのほうが大きければ更新あり（3 節） |
| 知らせる場面 | 新しい版があるとき。手動の確認では「最新」「失敗」も知らせる |
| 失敗時（自動） | 利用者には知らせず、ログ（`update   :`）に出すだけ |
| 設定 | [mxv2 の設定] の [通信] グループ（ON/OFF・次の時刻・[今すぐ…]） |
| 保存 | `mxv2.ini` の `[Network] UpdateCheck` / `NextUpdateCheck` |
| 対応環境 | Windows（WinHTTP）・Android（HttpURLConnection）。それ以外は [通信] ごと出さない |

## 1. 調査: GitHub で使える仕組み

公開場所は `Profile.ini` の `[URL] Project = https://github.com/gorry/mxv2`。
Releases にはタグ名 = 版番号（`2026.0918.1` など。`[Version] Text` と同じ書式）で
公開されていて、`mxv2_android_<版>.apk` と `mxv2_win64_<版>.zip` が添付されている。
本文は日本語の変更点の箇条書き。

| 方式 | 得られるもの | 制限 | 評価 |
|---|---|---|---|
| ① Releases API `releases/latest` | JSON（タグ名・日時・本文・添付の URL） | 認証なしは IP ごとに 1 時間 60 回 | **採用** |
| ② `github.com/<o>/<r>/releases/latest` | 302 の Location にタグ名 | API の回数制限の外 | 軽いがタグ名だけ |
| ③ `releases.atom` | 最近のリリース一覧（XML） | 同上 | XML を読む手間の割に得がない |
| ④ リポジトリに `version.json` を置いて raw で読む | 自由 | 数分のキャッシュ | 公開のたびに更新が要り、Release とずれうる |
| ⑤ GitHub Pages に同様のファイル | 自由 | 同上 | Pages を使っていないので準備が増える |

①を選んだ理由:

- 今の公開手順（タグを打って Release に zip/apk を添付）のまま、手間が増えない。
- **下書きとプレリリースは `latest` に出てこない。** 試験用の版はプレリリースで
  公開すれば、利用者には知らせずに済む。
- 1 日 1 回なら回数制限（60 回/時）は問題にならない。

実測で分かったこと:

- ETag を添えた条件付きの問い合わせは `304 Not Modified` になるが、
  **認証なしでは 304 でも回数を 1 消費した**（`X-RateLimit-Remaining` が減った）。
  文書の「304 は数えない」は認証付きの話らしい。したがって ETag は使っていない。
- 応答 JSON には、入れ子の `author` などにも `html_url` がある。**最上位のキーだけを
  見る**必要がある（4.3）。

## 2. 仕様（ユーザーの指示）

- GitHub Releases API を使う。
- Android は通信許可のパーミッションを追加する。
- 更新チェックは 1 日 1 回。
  - 成功時には更新通知ダイアログを出し、次の更新チェックを 24h 後に設定する。
  - 失敗時はユーザーには通知せず、次の更新チェックを 24h 後に設定するのみ
    （ログには失敗した旨を出力しておく）。
- アプリが通常使用可能となった後、別スレッドで API 発行と確認を行う。
  バージョンアップを検知した場合、メインスレッドにそれを通知し、
  メインスレッドから更新通知ダイアログを出す。
- 更新通知ダイアログは、通知メッセージと、GitHub のリリースページを開くボタンを出す。
- [mxv2 の設定] ダイアログに [通信] グループを追加する。
  - 次の更新チェック時刻を表示する。
  - [更新チェックを行う] チェックボックス。初期値は ON。OFF 時は更新チェックをしない。
  - [今すぐ更新チェックを行う] ボタン。24h 間隔を無視してすぐ更新チェックを行う。
    こちらは失敗した場合にダイアログで通知する。

### 2.1 仕様に書かれていないところの判断（実装側で決めた）

| 論点 | 決めたこと | 理由 |
|---|---|---|
| 「成功時」の意味 | 自動の確認で**新しい版があったときだけ**ダイアログ。最新ならログだけ | 毎日「最新です」と出すのは煩わしい |
| 手動の確認で最新だった | 「お使いのバージョン … は最新です。」をダイアログで出す | 押した結果が見えないと、押せたのか分からない |
| 手動の確認と 24h の送り | 手動でも次を 24h 後へ送る | 手動の直後に自動でもう一度確かめないため |
| 次を送るタイミング | **確かめ始めた時点**（終わった時点ではない） | 通信の途中で終了しても、同じ日に何度も確かめない |
| OFF でも [今すぐ…] | 押せる | 利用者の明示の操作なので |
| 「通常使用可能」の定義 | 起動時の警告とチュートリアルが済んだあと（`!tutorialPending && !tutorial.active()`） | チュートリアルの幕に割り込まない |
| チュートリアル中の結果 | 自動の結果は預かって、済んでから出す。手動の結果はすぐ出す | 手動は利用者が押したものなので |
| 手動の結果の出し場所 | [mxv2 の設定] が開いたままなら**その中に入れ子で**出す。閉じていればほかのダイアログが閉じるのを待って単独で出す | 設定画面を閉じさせずに結果を見せる |
| Android のバックグラウンド | 裏にいる間は確かめない（前面の描画ループでだけ判定） | 前面へ戻った時点で時刻を過ぎていれば確かめるので実害がない |
| 使えない環境 | [通信] グループそのものを出さない | HTTP の実装が無い環境（Windows・Android 以外）や、公開場所が GitHub でない場合 |
| 同じ版を繰り返し知らせる | 知らせる（「今後出さない」は無い） | 仕様どおり。要望があれば足す |
| 何をもって更新とするか | `[Version] Text` とタグ名の比較。**公開版のほうが大きいときだけ**新しいとみなす（詳細は 3 節） | 手元のビルドは公開版より新しい番号のことがある（開発中は .2 に対して公開 .1） |
| 開くページ | 応答の `html_url` が公開場所の下（`MXV2_URL_PROJECT + "/"` で始まる）ならそれ、違えば `<Project>/releases/latest` | 応答の URL をそのままブラウザへ渡さない |

## 3. 更新の判定

仕様（2 節）には「何をもって更新されたとするか」の定めが無く、実装側で決めた。
**2026-09-24 にユーザーが「`Profile.ini` の `[Version] Text` と API で取得できる
タグを比較している」ことを確認した。**

### 3.1 比べる 2 つ

| 側 | 値 | 出どころ |
|---|---|---|
| 手元（今動いているアプリ） | `MXV2_APP_VERSION`（例 `2026.0918.2`） | `Profile.ini` の `[Version] Text`。CMake が `appprofile.h` へ写す（`appprofile.h.in` の `#define MXV2_APP_VERSION "@MXV2_VERSION_TEXT@"`）。Android の `versionName` も同じ値 |
| 公開（GitHub） | 最新リリースの `tag_name`（例 `2026.0918.1`） | `releases/latest` の応答 JSON の最上位のキー。下書きとプレリリースは含まれない |

`[Version] Number`（`202609182` のような整数。Android の `versionCode`）は
**使っていない**。タグ名に対応するものが無いため。

### 3.2 比べ方（`UpdateChecker::CompareVersions`）

1. 頭の `v` / `V` は読み飛ばす（`v2026.0918.1` のようなタグにも備える）。
2. 残りから**数字の並びを 1 つの数として**順に取り出す。数字以外の文字は
   すべて区切りとして読み捨てる。
   `2026.0918.2` → (2026, 918, 2)。先頭の 0 は数としては消える（`0918` → 918）。
3. 頭から順に数で比べ、最初に違ったところで大小を決める。桁数の足りない側は
   0 とみなす（`2026.0918` と `2026.0918.0` は同じ）。
4. **タグ > 手元 のときだけ「更新あり」**（`UpdateResult::kNewer`）。
   同じか手元のほうが大きいときは「最新」（`kLatest`）。

| 手元 | タグ | 判定 |
|---|---|---|
| 2026.0918.1 | 2026.0918.1 | 最新 |
| 2026.0918.1 | 2026.0918.2 | 更新あり |
| 2026.0918.2 | 2026.0918.1 | 最新（手元の開発中のビルドのほうが新しい） |
| 2026.0918.9 | 2026.0919.1 | 更新あり（2 つめの数で決まる） |
| 2026.0918.1 | v2026.0918.2 | 更新あり（頭の v は読み飛ばす） |

### 3.3 前提と注意

- **タグ名を `[Version] Text` と同じ書式で付けること**が前提。今の Releases は
  そうなっている（`make arc` の成果物名 `mxv2_win64_<版>.zip` とも同じ）。
- 2 つめ・3 つめの欄は**文字列ではなく数**で比べる。`0918` と `918` は同じ、
  `0918.10` は `0918.9` より新しい。書式を変えて「月日」の欄の桁数が変わっても
  数としての大小が保たれていれば判定は崩れない。
- 数字以外は読み捨てるので、`2026.0918.1-beta` のようなタグは `2026.0918.1` と
  同じ扱いになる。ただしプレリリースは `releases/latest` に出てこないので、
  プレリリースとして公開している限り実害はない。**通常のリリースに
  サフィックス付きのタグを付けると、同じ数の版と区別できない**点に注意。
- 公開した版より手元の版を大きくしておけば（開発中は `.2` など）、手元の
  ビルドで「更新あり」が出ることはない。逆に、公開版を試験するときは 5.2 の
  方法で手元の版を古くする。

## 4. 実装

### 4.1 ファイル構成

| ファイル | 役割 |
|---|---|
| `src/httpget.h` / `.cpp` | HTTPS で 1 つの URL を GET する。Windows は WinHTTP、Android は JNI で `HttpBridge`、その他は「使えない」 |
| `android/.../HttpBridge.java` | `HttpURLConnection` で GET。戻り値は `{ 状態番号, 本文, 誤り }` の 3 つ |
| `src/updatecheck.h` / `.cpp` | `UpdateChecker`（作業スレッドの起動・結果の受け渡し）、JSON の最上位の文字列の抽出、版の比較 |
| `src/settingsui_update.cpp` | [通信] グループ（`BuildNetworkGroup`）、結果のダイアログ（`BuildUpdateWindow`）、どこで開くかの判断（`ScheduleUpdateWindow`） |
| `src/main.cpp` | いつ確かめるかの判断、結果のログ出力（`LogUpdateResult`）、UI への受け渡し |
| `src/settings.*` | `[Network] UpdateCheck`（既定 1）/ `NextUpdateCheck`（UNIX 秒）。フィールドは `kFieldUpdateCheck` / `kFieldUpdateSchedule` |
| `AndroidManifest.xml` | `android.permission.INTERNET` を追加 |
| `CMakeLists.txt` | 上のソースを追加。Windows は `winhttp` をリンク |
| `assets/locale/*/message.ini` | `[Dialog] Update`、`[Button] OpenReleasePage`、`[Settings] Network` ほか、`[Log] Update*`、新しい節 `[Update]` |

`OpenUrl()`（既定のブラウザで開く）は `settingsui_info.cpp` の無名名前空間から
`settingsui_internal.h` の共有の小道具へ移した（バージョン情報と更新の知らせで共用）。

### 4.2 流れ

```
main ループ（前面のときだけ、ui.Build のあと）
  ├─ manual = ui.TakeUpdateCheckNow()
  ├─ 始める条件: 走っていない && (manual || (通常使用可能 && UpdateCheck && now >= NextUpdateCheck))
  │     → UpdateChecker::Start(manual)   … メインスレッドで httpget::Prepare()、作業スレッドを切り離して起動
  │     → NextUpdateCheck = now + 24h、ini へ（kFieldUpdateSchedule）
  ├─ UpdateChecker::Poll(&r) で結果を拾う
  │     → LogUpdateResult(r)            … "update   : …" を 1 行
  │     → 新しい版 or 手動なら預かる
  └─ 預かった結果を ui.ShowUpdateResult(r)（チュートリアル中は自動の結果だけ待たせる）

SettingsUi::Build
  ├─ ScheduleUpdateWindow()  … 手動 && 設定画面が開いている → 入れ子で開く印
  │                             それ以外 → anyDialogOpen() が偽になるのを待って単独で開く印
  ├─ 単独なら BuildUpdateWindow()（最上位で組む）
  └─ BuildSettingsWindow の中: [通信] グループ、入れ子なら BuildUpdateWindow()
```

作業スレッド（`UpdateChecker::ThreadMain`）:

1. `MXV2_URL_PROJECT` から `<owner>/<repo>` を取り出し、API の URL を作る。
2. `httpget::Get(api, "mxv2/<版>", "application/vnd.github+json", ...)`。
   GitHub の API は User-Agent が必須。
3. 状態番号が 200 以外なら失敗（404 はリリースが 1 つも無い、403/429 は回数制限）。
4. 最上位の `tag_name` と `html_url` を拾い、`MXV2_APP_VERSION` と比べる（3 節）。

### 4.3 作りの要点・踏んだところ

- **作業スレッドとの受け渡しは参照カウント。** 結果の置き場（`State`）を本体と
  作業スレッドの 2 者で持ち、最後に手を離した側が消す。本体の破棄時に通信中なら
  **待たずに**手を離す（終了を通信の時間切れまで待たせない）。スレッドは
  `SDL_DetachThread` で切り離し、完了は `SDL_atomic` の `done` で見る。
- **Android の FindClass はメインスレッドから。** 作業スレッドのクラスローダからは
  アプリのクラスが見えない（`safaccess.cpp` と同じ事情）。`Start()`（メインスレッド）で
  `httpget::Prepare()` を呼んで jclass をグローバル参照で掴み、作業スレッドでは
  `SDL_AndroidGetJNIEnv()` で attach してから呼ぶ。
- **JSON は最上位だけを見る最小の走査。** 入れ子のオブジェクト・配列・文字列は
  括弧の対応とエスケープだけ見て読み飛ばす。`\uXXXX`（サロゲートの組を含む）は
  UTF-8 に直す。外部の JSON ライブラリは入れていない。
- **ImGui のポップアップの id は、開いた場所の id スタックで決まる。** 入れ子で
  開いた結果のダイアログは、[mxv2 の設定] の Begin/End の中で組まないと
  `IsPopupOpen` が食い違う。そのため `updateNested_` で「どこで開いたか」を覚え、
  同じ場所で組む。設定画面が先に閉じたら（子も ImGui が一緒に閉じる）控えを戻す。
- ESC（`CloseDialog`）は結果のダイアログを設定画面より先に閉じる。
  `anyDialogOpen()` に `updateOpen_` を入れ、ほかの操作と重ならないようにした。
- WinHTTP のプロキシは `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`（Windows 8.1 以降）で開き、
  開けなければ `DEFAULT_PROXY` で開き直す。時間切れは 15 秒。本文は 1MB で打ち切る。
- 時刻は 32 ビットに収まらなくなる日が来るので、ini には文字列で読み書きする
  （`Ini` に 64 ビットの整数の読み書きが無いため）。
- 表示する「次の更新チェック」は地方時で `YYYY-MM-DD HH:MM`。確かめている最中・
  OFF・時刻を過ぎている（まもなく確かめる）ときは、それぞれ別の文言にする。
- **Bash の heredoc で `\n` を含むパッチを書くと、本物の改行になって壊れる**
  （今回も `printf("…\n")` で踏んだ）。バックスラッシュを含む編集は Edit か、
  Write で書いたスクリプトで行うこと。

## 5. 検証

### 5.1 Windows（Debug、`-userdir` に使い捨てのフォルダ、`-skin Default`）

| 場面 | 結果 |
|---|---|
| まっさらな ini で起動 | 自動で確かめ、ログに「最新のバージョンです（公開 2026.0918.1、今のバージョン 2026.0918.2）」。ダイアログは出ない。`NextUpdateCheck` が 24h 後で保存される |
| [通信] を開く | チェックボックス（ON）、「次の更新チェック: 2026-09-25 23:05」、[今すぐ…] が出る |
| [今すぐ…] | 設定画面の中に「お使いのバージョン 2026.0918.2 は最新です。」。ESC で結果だけ閉じ、設定画面は残る。次の時刻も送られる |
| 新しい版がある（試験用ビルド） | 起動しただけで「新しいバージョン 2026.0918.1 が公開されています。」「お使いのバージョン: 2026.0101.1」と [リリースページを開く] [閉じる]。[閉じる] で閉じる |
| 失敗・自動（試験用ビルド） | ログに「更新の確認に失敗しました: HTTP 404」。ダイアログは出ない |
| 失敗・手動（同上） | 「更新の確認に失敗しました。」と薄い字で「HTTP 404」 |
| チェックを OFF | 「更新チェックは行いません」、ini は `UpdateCheck=0` |

[リリースページを開く] はデスクトップにブラウザが立ち上がるので押していない。

### 5.2 公開版より新しい手元の版で「新しい版がある」「失敗」を試す方法

手元の版が公開版より新しいと「最新です」しか出ない。`Profile.ini` は著作者専用で
触らないので、**ビルド先に生成されるヘッダー**を一時的に書き換える:

1. `build/win64/generated/appprofile.h` を退避する（ハッシュを控える）。
2. 「新しい版がある」: `MXV2_APP_VERSION` を古い番号（例 `"2026.0101.1"`）にする。
   「失敗」: `MXV2_URL_PROJECT` を存在しないリポジトリ（例 `.../mxv2-no-such-repo`）に
   する → API が 404 を返す。
3. `make build-windows` で作り、使い捨ての `-userdir` で起動して確かめる。
4. 退避したヘッダーを戻し、ハッシュが一致することを確かめてから作り直す。

### 5.3 Android（Pixel 7a、release）

- 起動して自動で確かめ、logcat に `update   : 最新のバージョンです（…）`。
- ini の `[Network]` に `UpdateCheck=1` と 24h 後の `NextUpdateCheck`。
- `dumpsys package` で `android.permission.INTERNET: granted=true`。
- [通信] グループの画面と、Android での手動の確認のダイアログは見ていない
  （組み立てるコードは Windows と同じ）。

## 6. 積み残し・今後の案

- 同じ版の知らせを「今後出さない」（スキップ）機能は無い。
- リリースの本文（変更点）はダイアログに出していない（仕様どおり）。出すなら
  `body` を 4.3 の走査で拾える。
- アプリ内でのダウンロード・インストールはしない。Android で apk を入れさせるには
  「提供元不明のアプリのインストール」の許可が要り、Windows は実行中の exe の
  差し替えが要るため、ブラウザでリリースページを開くところまでにしてある。
- 回数制限（60 回/時・IP ごと）に当たった場合は 403/429 で失敗扱いになり、
  翌日また確かめる。
